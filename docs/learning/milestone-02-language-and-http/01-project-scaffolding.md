## Current server compiler decisions

| Setting | Current value | Reason and limit |
| --- | --- | --- |
| include, at project top level | src/**/*.ts | Select initial TypeScript inputs; imported dependencies can also join the program |
| rootDir | ./src | Establish the source base for preserved output paths; does not select inputs |
| outDir | ./dist | Separate emitted files from source |
| module | nodenext | Model Node module behavior for output run directly by Node |
| server package type | module | Explicitly interpret this package's emitted .js files as ES modules |
| target | es2024 | Fixed language-output baseline informed by the community Node 24 preset |
| lib | es2024 | Standard JavaScript API declarations without adding browser DOM globals |
| types | node | Include Node global declarations |
| sourceMap | true | Retain source mapping alongside emitted JavaScript |

Strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes, verbatimModuleSyntax, isolatedModules, noUncheckedSideEffectImports, moduleDetection force, and skipLibCheck remain from the generated configuration. They have not each been independently explained or assessed. Template JSX, declaration, and declarationMap options were removed because this application does not currently require those outputs.

ES2023 was initially proposed conservatively. After the learner challenged ESNext and asked about best practices, the tutor checked current guidance and refined the proposed baseline to ES2024. Matching the runtime and delivery pipeline is the principle; a fixed target or one particular version is not a universal requirement. NodeNext itself models evolving Node rules and is not an exact Node 24 version pin.

## Development workflow decision

Learner correctly explained that start executes the existing compiled index.js, which must be rebuilt to reflect edits to index.ts. This is an independent explanation of artifact freshness after the earlier path and command support.

Tutor compared three valid options: compiler watch plus Node watch, tsx source execution/watch with separate type checking, and Node's native TypeScript/watch with its syntax and runtime-configuration limitations. Learner chose to reuse the compiler pipeline to avoid an additional runner dependency or native TypeScript limitations. This is a reasoned preference, not evidence that the alternatives are generally unsuitable.

The planned loop has separate jobs: the compiler watches source and updates generated JavaScript; Node watches generated JavaScript and restarts execution. The learner implemented dev:build as tsc --watch and dev as node --watch ./dist/index.js; Codex verified both entries. The initial dev:build value used the build script label as an executable; tutor clarified the distinction and learner replaced it with tsc. The existing one-shot scripts are preserved. Learner reported both watchers responded to a comment change, then both showed failures after an unspecified introduced error. Codex found the comment in source and emitted JavaScript; the introduced error was no longer present, and its exact diagnostics/runtime failure were not captured. No watcher processes were started or stopped by Codex.

## Watch failure-policy decision

[TypeScript noEmitOnError](https://www.typescriptlang.org/tsconfig/noEmitOnError.html) defaults to false, allowing emission despite diagnostics. Reporting a compiler error therefore does not by itself establish that the generated artifact was held back, that Node failed for the same reason, or that a watcher stopped watching. The learner chose to continue emitting despite errors. The current default already implements that preference, so no compiler configuration was changed. Exact errors from the earlier experiment remain unknown, and no controlled type-only-error experiment was performed. This closes the preference question without claiming a validated error experiment or successful business behavior.
